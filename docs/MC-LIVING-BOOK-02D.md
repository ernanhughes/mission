# MC-LIVING-BOOK-02D — Evaluated Experience and Transfer

Status: **Phase A complete; Phase B design frozen; pilot runs pending.**
This is a research pilot, not a claim that the Living Book has learned.

## Purpose

The commission separates four things that earlier surfaces deliberately kept apart:

1. a proposal generated by a model;
2. an author decision about that proposal;
3. an independent, versioned evaluation of its quality;
4. demonstrated transfer of a lesson to different held-out work.

Owner acceptance remains context, never proof. A failed, missing, negative or contradicted
evaluation remains visible and cannot become a proven lesson.

## Phase A — read-only evaluation of a retained proposal

Before this phase, a chapter proposal could only be evaluated inside the generation DAG
(`chapter.evaluate`). There was no route to evaluate an already-retained proposal, and stopped
runs were never resumed. The documentation independent-evaluation endpoint uses a different
workflow and rubric, so it cannot evaluate chapter proposals.

The smallest reusable path is now implemented in ALIVE:

| Piece | Location |
| --- | --- |
| One-stage workflow `chapter-evaluation` v1 | `alive/workflows/builtin/chapter-evaluation.v1.json` |
| Capability `chapter.independent_evaluate` v1.0.0 | `alive/capabilities/manifests/chapter.independent_evaluate@1.0.0.yaml` |
| Versioned rubric `chapter-evaluation-v1` | `alive/chapter_workflow/evaluation_contracts.py` |
| Deterministic preservation checks | `alive/chapter_workflow/evaluation_preservation.py` |
| Retained-artifact reload and quote checks | `alive/chapter_workflow/evaluation_adapters.py` |
| Owner admission, Grant, receipt | `alive/chapter_workflow/evaluation_service.py` |
| Read-only HTTP surface | `alive/chapter_workflow/evaluation_api.py` |
| Offline infrastructure tests | `alive/tests/test_chapter_evaluation.py` |

The route accepts one source run, proposal artifact id, artifact hash, proposal text hash,
original text/hash, criteria and rubric version. The source run must belong to the workspace;
the proposal must be the retained `workflow_result` of that run; the proposal text hash must
match; the current pinned source approval must match the run's original. The adapter reloads the
artifact and rechecks every identity at dispatch. It never calls the improve stage, writes a
manuscript, records a decision or changes promotion.

The workflow evaluates against six fixed dimensions (`technical_preservation`,
`argument_preservation`, `clarity`, `economy`, `completeness`, `provenance_integrity`) on a 0–4
scale. The model must quote both versions and address every mechanical attention item. The seven
mechanical checks are presence checks only: a pass is not proof of meaning preservation, and an
attention item is not proof of harm.

### What this pilot can and cannot test

**H1 is testable:** does adding the workspace's existing context-only experience change the
quality of a later chapter proposal compared with no experience?

**H2 is not testable in this pilot.** There is no independently evaluated lesson. The only
eligible owner decision is chapter 14's accepted economy proposal, and its evaluation failed at
the old token ceiling. It remains `quality_unverified` and `promotable: false`. Using it as
context is permitted; calling it a proven lesson is not.

**No irrelevant-experience arm is run.** Only one eligible decision exists. Creating a second
item would require a new owner decision before the experiment, and without it relevance
specificity cannot be separated from the effect of added context.

The evaluator is blind to condition, experience, decision and the other arm, but it is the same
model family as the generator. It is not human or third-party review.

## Phase C — evaluation and outcome rules

Both proposals are evaluated independently with the frozen rubric. A comparison is valid only
when both improvement runs complete with the exact frozen plan, source and (for B) experience
context hash, and both evaluations complete with valid quotes.

The pre-registered labels are:

- `benefit_observed`: B is `benefit`, A is not, B's total and economy rubric deltas exceed A's,
  preservation attention does not increase, guardrails do not fall, and every attention item is
  explained.
- `harm_observed`: B is `harm`, a guardrail delta is negative, attention increases, or B's total
  delta falls below A's.
- `no_benefit_observed`: valid comparison, neither of the above.
- `inconclusive`: failed evaluation, missing receipt or identity, un-injected context, or
  conflicting signals.

`benefit_observed` describes one pre-registered pair. It does not establish learning, quality or
general transfer.

## Phase D — author-facing comparison

After the runs, the Mission Living Book improvement surface will show, for each proposal:

- the retrieved experience and its evidence status;
- the comparison condition (A/B) without presenting B as a treatment that works;
- the independent evaluation, rubric dimensions and mechanical attention items;
- run ids, model calls, tokens and receipts;
- the neutral conclusion label, uncertainty and limitations.

Re-evaluating a retained proposal from the UI remains deferred until the backend path is
qualified; the backend path is now qualified for one proposal.

## Non-claims

- The B condition is not proven learning.
- Owner acceptance is not quality evidence.
- A model verdict is not publication readiness.
- One pair is not statistical evidence and does not establish transfer.
- The evaluator shares a model family with the generator.
- No manuscript was edited, promoted or deployed.
