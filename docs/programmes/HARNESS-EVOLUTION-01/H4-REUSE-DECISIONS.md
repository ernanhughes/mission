# H4 targeted reuse decisions

| System | Existing mechanism inspected | H4 decision |
|---|---|---|
| Worker | `src/schema/request.ts` (`WorkRequest`), `src/core/worker.ts` job lifecycle/cancel/result handling, `src/executors/types.ts` `WorkExecutor`/`ExecutorRegistry`, `src/executors/model.ts`, `src/models/runtime/engine.ts`, provider adapters, `src/core/execution-ledger.ts` and `execution-summary.ts`. | Extend the existing model request and ModelExecutor path only when an explicit `execution.strategy_id` is present. Keep the H3 execution ledger and parent Worker request as authority. Runtime `execution_id` values identify each child model call. Existing requests without a strategy remain byte-for-byte on their old execution path. No separate engine or ledger. |
| Worker model routes | `worker.models.yaml`: `capability_deepseek_free`, `capability.free`, explicit one-attempt policies; `OpenCodeProvider` supports the existing chat adapter. | Use the existing OpenCode chat adapter with a named loopback Ollama route and one-route policy for the bounded H4 model comparison. Keep default model policy unchanged. Paid/subscription strategy routes are blocked because current provider receipts do not enforce a maximum monetary charge. |
| Worker structured output | `src/models/runtime/types.ts` has a `structured_response` capability requirement, but `ProviderRequest`/`OpenCodeProvider` currently have no generic JSON Schema response-format parameter. | H4 B/C use public structural constraints in the prompt and the existing-installed `ajv` package for internal validation. Do not claim native provider enforcement. Do not inspect evaluator answers. |
| Writer | `packages/writer-core/writer_core/utils/json_text.py` provides recursive schema validation; `packages/writer-ai/writer_ai/utils/model_result_parser.py` parses a Writer-specific format. `writer-ai/writer_ai/eck/kernel/repair.py` and `eck/domains/writing/llm_repair.py` provide Writer-domain repair. | Reuse the structural-validation pattern, not a Writer import: Python Writer packages are not Worker runtime dependencies and their repair semantics are Writer-specific. H4 does not add a new generic string-repair helper; correction is a second bounded model invocation based only on structural validation feedback. |
| Shared AI package | `C:\Projects\ai\src\ai\inference\service.py` uses Pydantic structured validation, explicit budgets, usage and trace; malformed output raises. It does not auto-repair malformed output. | Reuse the fail-closed distinction and budget accounting concepts. Do not add a cross-process AI service dependency or copy its provider invocation stack into Worker. |
| Praxis | `praxis/harness.py` defines `HarnessPolicy`, `HarnessState`, `run_harness`, and bounded steps/wall time. `praxis/harness_recovery.py` is marked `RESEARCH_ONLY`; `PRAXIS-CAPABILITY-01-REPORT.md` records H05 no-fault false recovery and retirement from active path. | Do not port the generic model-facing recovery controller. Keep H4 to three fixed typed strategies, one correction maximum, deterministic validation, no policy selection or learning. Carry the small lifecycle and effectiveness-reference interface forward only for H5 design. |
| ECK | Writer ECK kernel action/policy/repair types, including `RepairRequest` and domain-specific `WritingRepairExecutor`. | H4 strategy recommendations can later map to a Worker `strategy_id`; no ECK dependency or Writer-domain semantics in Worker. |
| Mission Control | Existing Work Outcome `EpisodeService`, observation/evaluation contracts; uncommitted W8 `EnvelopeService`/`work_envelopes` API provides an authorized intent digest and execution links. | H4 records `task_id`, `episode_id`, Worker parent `request_id`, and child model execution IDs. Demonstrate episode resolution using isolated SQLite. Do not mutate operational Work Outcome data or extend the concurrent W8 WIP. H6 owns full integration. |
| Workbench | `src/workbench/service.py`, `ActionSpec` adapter contracts, and `docs/design/WB-06A-AUDIT-WORKBENCH-WORKER.md`. | No H4 Workbench changes. Existing Worker request API and `worker run --file` are sufficient user-facing controls. Workbench configuration is a later integration. |
| Remembering / Relate | Worker packages and APIs are present; H3-H4 task is a stateless public-fixture inspection. | Do not invoke memory, relationship, retrieval, or similarity mechanisms. No context-memory contract is needed for H4. |

No existing implementation provides a generic Worker-owned versioned A/B/C strategy runner with bounded whole-strategy accounting and Worker execution-ledger provenance. The narrow strategy composition is therefore added to Worker, while provider invocation, routing, and evidence stay on existing interfaces.
