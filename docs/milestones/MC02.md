# MC02 — Registry and persistence

## Delivered

- SQLite schema with explicit numbered SQL migrations and `schema_migrations`
- Shipped YAML defaults for applications, projects, books and outcomes
- Repository entity, project/repository links and typed relationships
- Application CRUD API/UI with identity, filesystem, launch, monitoring, relationships and control policy
- Multiple named launch definitions per application, each independently enabled/verified
- User overrides stored in SQLite
- Startup seed that inserts missing defaults only

## Precedence verified

Tests change an application's name/pin state and a book/project order, restart the app against the same database, and confirm the user values remain unchanged. Re-running `seed_defaults` does not overwrite custom values.

## Executable evidence

- `test_registry_and_projects.py::test_application_crud_and_launch_configuration`
- `test_registry_and_projects.py::test_user_application_configuration_survives_restart`
- `test_registry_and_projects.py::test_checkpoint_resume_and_priority_survive_restart`
- `test_migrations_and_seed.py` (migrations repeatable; expected tables; seed precedence; defaults do not enable unverified launches)

## Safety characteristics

- Unknown extra request fields are rejected.
- Paths are absolute; traversal rejected.
- A launch definition can be saved incomplete for diagnosis but is marked misconfigured and cannot silently pretend to be available.
